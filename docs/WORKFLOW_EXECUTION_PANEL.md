# Workflow Execution Panel & Output System Architecture

This document outlines the logic, systems, and UI architecture involved in tracking workflow executions and rendering their outputs within the execution panel.

## Overview

The Execution Panel (`workflow-progress-panel.tsx`) is responsible for providing users with real-time feedback on their workflow runs. It tracks individual node executions, maps their statuses (e.g., pending, running, success, failed), and safely renders the final execution payload.

The system is designed to handle potentially massive JSON payloads (like those generated by data processing or LLM outputs) without degrading browser performance, taking inspiration from robust monitoring dashboards like Inngest or Vercel.

---

## Core Systems & Data Flow

### 1. State Tracking & Reactivity

- **React Query / tRPC**: The panel relies on asynchronous data fetching (e.g., `executionRawOutputQuery`) to pull execution status and payloads.
- **Auto-fetching**: When a workflow execution becomes active or completes, the UI automatically requests the output payload. It strips out legacy manual interventions (like requiring users to click a "Load output" button) in favor of a seamless auto-load experience.
- **Status Mapping**: Each step or node execution state maps to a specific visual configuration (`workflowStateConfig`), which dictates the icons, spinners, and colors used in the UI.

### 2. Output Payload Section (The "Out" Section)

The output section handles the display of the final JSON evaluation or error stack trace returned by the workflow.

Because workflow outputs can range from small boolean values to massive multi-megabyte JSON arrays, the output viewer enforces strict rendering safeguards:

#### Safely Rendering Large Payloads

- **Threshold Limit**: The panel calculates the stringified length of the payload. If the payload is determined to be over ~1MB (specifically `> 500,000` characters), it triggers a safety mechanism.
- **Large Payload Warning**: If the payload exceeds the threshold, the UI blocks inline syntax-highlighted rendering to prevent React/DOM freeze-ups. Instead, it displays a warning stating the payload is too large to render inline safely.
- **Download Raw**: For large outputs, a "Download Raw" button is provided. This converts the payload into a Blob and triggers a direct browser download, allowing users to inspect the massive datasets locally using external tools.

#### Inspection Tools

- **Inline Rendering**: For normal-sized payloads (under the limit), the JSON is rendered inline in a scrollable, syntax-highlighted block.
- **Expandable Modal**: An "Expand" button allows users to port the active payload into a full-screen `<Dialog>` component. This modal provides a much wider, more comfortable view for inspecting nested JSON objects without competing with the rest of the canvas UI.

### 3. UI/UX Details

- **Stable Layouts**: Activity spinners and status icons use `shrink-0` to maintain vertical alignment. This ensures that even if an execution step returns a profoundly long wrap-around error message, the icons stay perfectly formatted alongside the text.
- **Component Stitching**: The output viewer is integrated directly into the progress panel timeline, serving as the final chronological block of an execution. If an execution errors out, the output block natively adjusts to cleanly present the error details.

## File Architecture

- **`src/features/editor/components/workflow-progress-panel.tsx`**
  - **Role**: The main orchestrator of the execution view.
  - **Key State Variables**:
    - `executionState` (Current status)
    - `executionResult` / `executionRawOutputQuery.data` (The retrieved payload)
  - **Sub-components Used**: `<Dialog>` for expansions, `<Lucide Icons>` for status markers, `<Button>` for trigger actions.

## Developer Notes / Maintenance

- **State Management**: Historically, an `isRawOutputRequested` boolean was used to gate network requests. This has been deprecated in favor of enabled queries that fire automatically based on `activeExecutionId`. Ensure any new data queries follow this auto-load pattern rather than reverting to manual gates.
- **Component Performance**: If implementing new syntax highlighters (e.g., swapping `prism` for `shiki`), always ensure the `500,000` character limit remains in place, as syntax highlighting very large strings in JS is entirely synchronous and will lock the browser thread.
